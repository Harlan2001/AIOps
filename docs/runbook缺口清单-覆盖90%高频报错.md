# Runbook 缺口清单：覆盖 90% 高频报错该补哪几类

> 数据来源：GaussDB `dimple` 7 张错误/报警历史表的真实报错文本（数据库端归一化统计）。
> 结论先说：**现有 21 条规则对"高频报错"的覆盖其实已经很好，按报错条数算覆盖率 >95%。**
> 真正缺的是 **4 个还没建的类别**，外加给 2 个现有类补几个同义关键词。补齐后即可覆盖已知高频报错的绝大部分。

## 三、需要【新建】的 4 类 Runbook（按优先级）

### ★ 第 1 类：频繁撤单 / 大额撤单预警（最该补，合规高频）
- **建议 id**：`cancel_order_alert`，severity：warn
- **关键词**：`撤单次数`、`已撤单次数`、`大额撤单次数`、`预警阀值`
- **真实样例**：「金交所交易编码:xxx 品种的 Au(T+D) 合约的已撤单次数:5；预警阀值:10；撤单次数:5」
- **取证方向（你去 C/Java 里确认表名）**：撤单次数阈值/参数配置表；runbook 主检查核对该合约撤单阈值与实际次数。
- **根因**：撤单频率接近/超过合规预警阀值，存在频繁报撤单嫌疑。
- **处置**：核对交易策略是否异常、确认是否为程序化频繁报撤、必要时调整报单逻辑或申请阈值调整。

### ★ 第 2 类：基础数据/主数据配置缺失或不合法
- **建议 id**：`base_data_config_error`，severity：error
- **关键词**：`数据未设置`、`挂牌基准价不合法`、`保证金未设置`、`席位号不存在`、`基准价`
- **真实样例**：「品种 ni 数据未设置」「[合约=>au2412] 挂牌基准价不合法」「合约 SHAU 交割保证金未设置」
- **取证方向**：品种/合约主数据表、基准价表、保证金配置表；核对该合约是否缺配置。
- **根因**：合约/品种的基础参数未配置或取值非法，业务无法正常进行。
- **处置**：在基础数据管理中补齐品种/合约参数、基准价、保证金配置后重新发起。

### ★ 第 3 类：系统初始化 / 状态错误
- **建议 id**：`system_init_error`，severity：error
- **关键词**：`初始化日期不正确`、`初始化前系统状态不正确`、`初始化在进行中`、`不能重入`
- **真实样例**：「初始化日期不正确」「初始化在进行中，不能重入」
- **取证方向**：系统状态表/初始化日志；核对当前系统状态与初始化日期。
- **根因**：系统未处于可初始化状态，或重复触发初始化。
- **处置**：确认当前系统状态、修正初始化日期、等待已有初始化完成后再操作。

### 第 4 类：报价参数错误（量小，可合并可单建）
- **建议 id**：`quote_para_error`，severity：warn
- **关键词**：`手工报价模式`、`最小报价量`、`报单数量小于`、`合约代码输入错误`
- **真实样例**：「当前为手工报价模式![第1腿]」「报单数量小于报价商最小报价量」
- **取证方向**：报价商参数表、最小报价量配置。
- **根因/处置**：报价模式或报价量不满足报价商规则，切换报价模式或调整数量后重报。

## 五、编写 Runbook 的硬性约束（务必遵守，否则启动失败）

1. **SQL 必须是简单单表查询**，禁止子查询、表别名、JOIN——fail-fast 校验器不理解别名作用域，会直接拒绝启动（已实测做不通）。
2. 同一列名必须在该 SQL 引用的表中真实存在；先查 `docs/error/GaussDB_dimple_全量表结构与字段含义清单.md` 确认表名和列名。
3. 需要跨表关联的字段（如会员反查），放到**采集层 Python** 处理，不要写进 runbook SQL。
4. 主检查 `primary: true` 取证成功 → 置信度 1.0；查不到/缺参 → 0.4。
5. 每个新类型在 `errors.yaml` 注册后，`runbook:` 字段指向新建的 rb 文件，文件名与 id 对应。
6. 取证表名不确定时，先在数据库里 `SELECT ... FROM 信息_schema.tables` 或对照全量清单，不要凭空写表名。
