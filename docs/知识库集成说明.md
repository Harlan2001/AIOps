## 1. 这次做了什么

在原有「ML 分流 / 相似案例召回 + 规则只读查库 + LLM 大脑」管线中，新增一个**领域知识检索节点**，
把 Dimple 官方知识库作为第三类证据接入：

| 证据 | 来源 | 回答 |
|---|---|---|
| 历史相似案例（先验） | ML 检索 `data/ml/dataset.csv` | 以前发生过多少次、长什么样 |
| 现场实时事实 | 规则引擎只读 SQL 查库 | 现在库里是什么状态 |
| **领域知识（本次新增）** | Dimple 知识库诊断卡 | 有哪些根因分支、成立/反证、只读 SQL、日志锚点、处置边界、恢复验证 |

LLM 综合三类证据出结论；规则快速路径（高置信 + 命中）不调 LLM，知识卡作为背景展示。

## 3. 配置 `config/kb.yaml`

```yaml
enabled: true                 # 总开关；关闭后静默跳过，不影响主流程
kb_root: "D:/document/dimple-knowledge-base-main"   # 容器内建议 /app/kb
audience: internal            # internal（内部全集，禁止外发）/ common / <客户ID>
baseline: ""                  # 空=用包基线（源码分析）；unknown=现场未核实，只返回通用取证
top: 3                        # 保留前 N 个父文档（1-10）
execute_kb_sql: false         # 关键：只读 SQL 默认不自动执行，仅作建议/展示
```

## 4. 关键设计与安全边界

1. **检索键用中文症状，不用数字错误码。** 编排传入 `normalize_skeleton()` 的骨架，
   `kb/client.py` 再用 `_clean_symptom()` 去掉 `[字段=>值]` 参数块、英文、数字，只保留中文业务短语
   （如"平仓错误 持仓不足 尚缺"）。实测知识库错误码体系与 TLOG.ERRCODE 不一致（数字码命中 0 条），
   中文症状命中准确。
2. **知识库只读 SQL 默认不自动执行（`execute_kb_sql=false`）。** 它仅作为建议喂给 LLM 与报告展示；
   必须经人工审核、核对现场方言/表结构/权限后，派生为规则引擎 runbook 才会执行。
   **唯一可执行查库层始终是规则引擎**（全程只读、写拦截、参数化绑定）。
3. **可降级**：知识库缺失/异常/关闭时 `available()=False`、`diagnose_card()=None`，主流程照常运行。
4. **客户/基线门禁**：`internal` 全集只能内部分析；交付客户必须用 `dimple_install.py
   skill/platform --audience <客户ID>` 生成客户专包；现场版本未核实传 `baseline=unknown`。
5. **诚实性**：知识卡与提示词都强制标注"冻结源码取证、未现场核实、只读 SQL 未执行"。
6. **零额外基础设施**：纯本地 BM25、纯标准库、离线、无网络/数据库/API key/向量库。

## 5. 运行方式

```powershell
$env:PYTHONIOENCODING="utf-8"

# 1) 知识库独立自测（不依赖 ML/数据/LLM，最先验证集成是否成功）
uv run python -m ai_ops.ops.kb_selftest

# 2) 端到端诊断（默认：高置信+规则命中走快速路径，零 token；报告含领域知识卡）
uv run ai-ops --id 4811525544

# 3) 强制走 LLM，看三证合一（历史案例 + 领域知识 + 现场查库）综合诊断
uv run ai-ops --id 4811525544 --llm

# 4) 直接粘贴文本
uv run ai-ops --text "[合约=>Au9999]结算价不存在"
```

## 6. 验证结果（已实测）

### 6.1 独立自测 `python -m ai_ops.ops.kb_selftest`
- 知识库加载成功：`kb-2026.10.14.2 / analysis-20261013.1 / internal`；
- 中文症状命中：持仓不足、结算价不存在、递延费率不存在、用户名或密码错误全部命中；
  持仓不足 Top 命中 `business-position-decision`（断言通过），含 missing-true-source /
  wrong-current-trade-owner / valid-position-transfer 等根因分支与处置边界；
- 错误路径降级测试通过（`available=False`、`diagnose_card=None`，不抛异常）。

### 6.2 端到端（`--id 4811525544`，Au(T+N1) 买持仓不足 1 手）
报告同时呈现：ML 分流（biz/0.994）、相似案例（历史 32 次）、规则查库（客户层买 1999、
明细 `TRADER_NO=None`）、3 张领域知识卡（含根因分支、只读 SQL、参数、来源）。

强制走 LLM 后，输出体现了知识库的增益：
- 准确指出"在指定交易员 trader 维度下可平不足 1 手，但明细 `TRADER_NO=None`，
  尚不能区分真实缺仓 / 交易员归属错误 / 重复超额平仓"，并声明证据不足以下定论；
- 明确写出"知识库只读 SQL 未在现场执行，不能据此认定现场状态"；
- 处置从泛泛 3 步扩展为 8 步：暂停任务→按成交号查成交→分层（客户层/交易员层/空交易员层）
  核算可平量→查 IF_TRADER_CTL 等参数→按权威证据分流（补录冲正 / 标准归属调整 / 持仓调转）
  →禁止虚增持仓改库→恢复后做数量守恒与下游核对、已切日按补偿冲正处理。

## 7. 部署到客户

1. 用安装工具生成**客户专包**（不要带 internal 全集）：
   `python installation/dimple_install.py skill/platform --audience <客户ID> --knowledge <知识库根> ...`
2. 将客户专包作为只读文件随镜像打入或挂载到 `/app/kb`，把 `config/kb.yaml` 的
   `kb_root` 指到该目录、`audience` 改为对应客户。
3. 知识包不含源码、凭据、客户数据（`manifest.contains_source_code=false`）；
   知识库更新走其自带的 `dimple-kb-update` 流程，产品侧只替换快照并回归。
