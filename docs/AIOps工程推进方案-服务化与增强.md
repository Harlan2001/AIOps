# DIMPLE AIOps 诊断平台工程推进方案（服务化与能力增强）

---

## 一、背景与目标

GaussDB 迁移改造已基本完成并验证通过：

- 20 个诊断 runbook（报错类型从 3 类扩至 20 类）全部对照 **977 张真实表结构清单**逐条核验，56 条取证 SQL 的表名/列名与库结构完全一致；
- 修复 3 项阻断级问题（YAML 语法、Oracle SQL 未迁移、SQL 执行零容错），诊断在库表缺失时降级不崩溃；
- 回归测试 33/33 全绿（含新增的"runbook 与表结构一致性"防线测试）；
- Oracle 时代遗留脚本已清理（ULOG.TLOG 回放、种子生成、样本校验 3 个专用脚本删除，LLM/管线中的 Oracle 文案更正）。

当前诊断内核（规则引擎 + GaussDB 错误历史取数）**能力已稳定，但对外形态仍是 CLI + Streamlit 演示壳**，存在三个结构性短板：

| 短板 | 现状 | 影响 |
| --- | --- | --- |
| 无 API 边界 | 能力只挂在命令行和 Streamlit 页面上 | 监控平台、IM 机器人、自动化任务无法调用诊断能力 |
| 单会话模型 | Streamlit 每次交互重跑脚本，无并发 | 无法无人值守批量诊断、无法被外部系统集成 |
| 能力不可沉淀 | 诊断结论只在页面/终端可见 | 无法形成可验收、可集成的服务资产 |

**本方案目标：不改动已稳定的诊断内核，把诊断能力工程化为"可服务、可评测、可交付"的形态**，支撑后续私有化交付与业务扩展。

## 二、阶段 2：诊断服务化（FastAPI 薄封装）

### 2.1 动机

诊断能力当前只能通过人机交互使用。服务化后，一条报错可以随时被系统调用，是走向"自动化运维闭环"的前提（告警 → 自动诊断 → 推送结论 → 沉淀案例）。

依赖层面已就绪：`pyproject.toml` 已预留 `api` 依赖组（FastAPI / uvicorn / pydantic），无需新增技术选型讨论。

### 2.2 方案内容

**① 抽取 service 层（纯重构，不改变行为）**
把 Streamlit 页面中的业务逻辑（取记录 → 诊断 → 组装报告数据）收敛到独立 service 模块，页面只保留渲染。这是服务化的地基，风险最低。

**② FastAPI 薄壳（只加壳，不重写内核）**
新增 API 服务，薄封装同一 service，建议端点：

| 端点 | 用途 |
| --- | --- |
| `GET /healthz` | 存活 + 深度自检（库连接、规则加载数） |
| `POST /v1/diagnose` | 单条诊断（支持直接传报错文本，或按来源/日期/主键取数） |
| `POST /v1/batch-diagnose` | 批量诊断（对应每日全量回放场景） |
| `GET /v1/records` | 按来源/日期查询错误记录（供前端表格） |
| `GET /v1/rules` | 规则与覆盖率清单 |

请求/响应用 pydantic 定义契约，数据库连接用依赖注入单例。

**③ 前端与集成策略**
第一阶段保留 Streamlit 作为演示壳，同时把 API 接入监控平台与 IM 机器人——运维场景中"机器人推送诊断结论 + 跳转详情"比重做前端更刚需。前端重做（如有需要）放后续单独评估。

**④ 部署与鉴权**
uvicorn 单进程起步；私有化环境先用接口密钥 + IP 白名单，后续按公司规范接入统一认证/网关。

### 2.3 预期收益

- 诊断能力被任何系统消费（监控、IM、自动化、外部平台），形成服务资产；
- 批量诊断可无人值守执行，覆盖"每日全量报错回放"场景；
- 为后续前端重做、移动端、机器人集成预留标准接口；
- 内核零改动，服务化风险集中在新增壳层，可随时回退。

## 三、阶段 3：能力增强（四项，按价值排序）

### 3.1 诊断链收敛：规则分流 + 查库取证 + LLM 兜底（去 ML）

**决策（最新）**：按领导意见，本项目**去除全部 ML 组件**——不再保留 ML 分流器，也不保留 TF-IDF 相似案例召回。原因：GaussDB 侧报错全部可从源码确定、日志无噪音样本，ML 分流/召回失去训练与增值前提；高频识别由确定性规则引擎即可完成，且规则可解释、可审计、私有化交付零模型文件。

**已完成（随本次去 ML 改造）**：

1. **分流规则化落地**：噪音识别用 `noise_rules.yaml` 关键词 + `parser.is_tech_error()`，业务类型识别由规则引擎关键词打分完成，快速路径决策由 `rule_hit` 命中决定——全部确定性、零训练；
2. **代码与资产清理**：删除 `ml/` 组件（router/retriever/dataset 5 文件）、3 个 Oracle 时代死脚本（`hybrid_replay`、`pick_samples`、引用已删 tlog 的 `llm_demo_batch`）、演示夹具与样本；删除模型文件（routing/biz_type joblib）与 23MB 训练集；pipeline/service/api/页面/CLI/doctor/paths 全部改写为无 ML 形态；
3. **依赖治理**：`pyproject.toml` 移除 scikit-learn/joblib/scipy/numpy 直接依赖（numpy 仅作为 streamlit 的传递依赖存在，非项目声明），`uv.lock` 已同步；
4. **回归防线**：39/39 测试全绿（原 40 − 1 个 retriever 测试），service/api 行为冒烟通过。

**落地形态（本次改造后的诊断链）**：入口过滤（自由文本过 `noise_rules` 关键词 + `is_tech_error()`；取数链路无噪音）→ 规则引擎 20 类型识别 → runbook SQL 查 GaussDB 取证 → `rule_hit` 命中走规则快速路径（零 token）→ 未命中走 LLM 兜底（KB 知识卡 + 规则取证两类证据）。

**观测基线（替代原 ML 评测）**：保留"LLM 调用降本率"（规则快速路径命中数 / 总诊断数）作为增强观测指标，随批量诊断累积量化；规则覆盖率口径与噪音过滤口径已在 coverage_scan 拆分展示。

### 3.2 规则加载期 fail-fast 校验

**现状**：runbook 与表结构一致性已固化为测试防线（CI 拦截），但运行时仍是"加载通过、诊断时降级"。

**做什么**：规则加载时用表结构清单校验每条 SQL 的表/列，启动即报错（fail-fast），把兜底从"运行时"提前到"启动时"。

**收益**：新增/修改 runbook 时错误暴露从"线上诊断静默降级"变为"上线前即拦截"，诊断结论可信度提升。

### 3.3 诊断降级可见化

**现状**：SQL 异常兜底已实现，但 CLI/页面未显式展示"本条诊断因某表缺失而降级"。

**做什么**：在 CLI 与工作台显式展示降级原因（sql_errors），让"推测表失效"可见而非静默。

**收益**：避免运维误把降级结论当完整诊断；同时倒逼表结构知识持续补齐。

### 3.4 配置与部署治理

- **多环境配置**：db 等配置支持环境变量与 dev/test/prod 多套 profile，覆盖脚本中残留的硬编码绝对路径；
- **容器化交付**：补齐 Dockerfile + 编排文件（基础材料已就绪），为私有化一键部署准备；
- **文档治理**：清理无关杂记文档、更正分支名笔误、同步改造总结文档的"待验证项"章节。
