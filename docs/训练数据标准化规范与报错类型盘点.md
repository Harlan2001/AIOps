# 训练数据标准化规范与报错类型盘点

## 文档说明

本文档涵盖以下内容：

- 现状盘点：现有报错数据与诊断规则的覆盖情况（第一、二章）；
- 标准化规范：训练数据的字段说明、骨架归一化、标签规则与填写模板（第三章）；
- 类别示例：各报错类别的标准化示例（第四章）；
- 录入示例：新增报错类型的完整录入流程（第五章）；
- 输出说明：程序诊断报告的结构与真实输出样例（第六章）；
- 录入流程：补充数据的操作步骤（第七章）。

---

## 一、数据层与规则层

系统对报错的处理分为两个层次，需先明确区分。

**数据层**：历史报错的原始记录，从系统日志中提取，逐条登记报错原文、时间、错误码等。回答"线上实际出现过哪些报错"。存放于：

- `data/rule_seed.csv`：业务报错，137 种
- `data/noise_seed.csv`：噪音流水，16 种
- `data/ora_seed.csv`：Oracle 技术错误，33 种
- `data/ml/dataset.csv`：机器学习训练集

**规则层**：针对特定报错编写的诊断方案，包含查哪张表、如何判断、根因与处置建议。回答"该报错是否已具备自动诊断能力"。存放于：

- `rules/errors.yaml`：登记纳入诊断的报错类型
- `rules/runbooks/rb_*.yaml`：各报错对应的具体诊断步骤

**两层通过报错关键词关联。** 以数据层一条 `[合约=>SHAG]结算价不存在` 为例，规则层登记了"结算价不存在"关键词，二者匹配后即触发对应的诊断方案。

由此产生一个现状：数据层登记 137 种报错，规则层仅覆盖其中 3 种。未覆盖的报错，或由大模型（LLM）临时处理，或无自动诊断。本文档即用于规范数据层的填写标准，并说明如何将未覆盖类型补入规则层。

## 二、现状盘点

### 2.1 数据层覆盖情况

| 文件 | 内容 | 规模 |
|------|------|------|
| `data/rule_seed.csv` | 业务报错骨架 | 137 种 |
| `data/noise_seed.csv` | 噪音流水 | 16 种 |
| `data/ora_seed.csv` | Oracle 技术错误 | 33 种 |
| `data/ml/dataset.csv` | 机器学习训练集 | 全量 FATAL 与 ERROR 级报错 |

137 种业务报错按粗类分布如下（源自 `rule_seed.csv` 的 `category` 列）：

| 粗类 | 含义 | 典型表现 |
|------|------|---------|
| 数据缺失 | 主数据/参数/记录查找不到 | 结算价不存在、系统参数不存在 |
| 操作失败 | 写入/修改/删除等动作未成功 | 修改失败、分户余额表增加失败 |
| 业务规则校验 | 当前状态或数据不满足业务规则 | 持仓不足、合约代码不能为空、不能重复复核 |
| 流程未就绪 | 前置流程未完成或未复核 | 成交信息不存在或未复核、清算未完成 |
| 录入校验 | 输入格式或长度不合规 | 合同号长度不为十五位 |
| 权限登录 | 账号/IP/安全标识异常 | 用户名或密码错误、IP 格式不合法 |
| 待分类 | 暂未归入上述类别，需人工核对 | 分配数量大于成交数据 |

### 2.2 规则层覆盖情况

`rules/errors.yaml` 共登记 3 个报错类型，各配一套诊断方案：

| 报错类型 | 诊断方案 | 诊断方式 |
|---------|---------|---------|
| 结算价不存在 | `rb_settle_price.yaml` | 查交易日历、查结算价表 |
| 递延费率不存在 | `rb_defer_fee.yaml` | 查交易日历、查递延费率表 |
| 平仓时持仓不足 | `rb_position.yaml` | 查客户持仓表、查持仓明细 |

此外，`rules/noise_rules.yaml` 含 13 个噪音关键词，命中即判为非故障并拦截；Oracle 技术错误本期不做诊断，种子数据备用。

### 2.3 覆盖差距

数据层有 137 种业务报错骨架，规则层仅 3 种已编写诊断方案。其余 134 种或由大模型兜底，或无自动诊断。补哪些类型、按何种优先级，由项目侧决定；本文档负责明确数据填写标准与录入流程。

## 三、训练数据标准化规范

### 3.1 数据来源

原始数据源自 Oracle 库 `ULOG.TLOG` 表（`LLEVEL IN (20,30)` 即 FATAL 与 ERROR 级日志），经 `tools/gen_rule_seed.py` 拉取并自动归类，产出 `rule_seed.csv` 等种子文件；经 `ml/dataset.py` 产出训练集 `dataset.csv`。

补充训练数据时，通常不直接连库，而是基于一批报错文本（工单、日志导出等），按下列规范整理为 `dataset.csv` 同结构记录。

### 3.2 字段说明

`dataset.csv` 共 12 个字段，按必填与选填分述如下。

**必填字段：**

| 字段 | 含义 | 示例 |
|------|------|------|
| `text` | 报错原文，须原样保留，不得改字 | `[合约=>SHAG]结算价不存在` |
| `skeleton` | 报错骨架，按 3.3 规则归一化 | `[合约=>?]结算价不存在` |
| `cls` | 一级分流标签，见 3.4 | `biz` |
| `ldate` | 日志时间，格式 `YYYY-MM-DD HH:MM:SS` | `2026-01-15 16:37:27` |

**选填字段（有则填，无则留空）：**

| 字段 | 含义 | 缺失时处理 |
|------|------|-----------|
| `id` | 报错流水号 | 手工补充时填递增序号 |
| `llevel` | 日志级别，20=FATAL，30=ERROR | 填 30 |
| `errcode` | 业务错误码 | 填 0 |
| `func_no` | 功能号 | 留空 |
| `biz_type` | 二级类型标签，仅 biz 填写 | 见 3.4 |
| `module` | 代码包名，自 lsection 解析 | 留空 |
| `deep_proc` | 过程名，自 lsection 解析 | 留空 |
| `lsection` | 调用栈原文 | 留空 |

### 3.3 报错骨架（skeleton）归一化

同一种报错每次出现的具体数值不同，但结构相同。将可变部分替换为占位符后得到的模板即为骨架，同一骨架下的报错归为同一类。归一化执行以下三步：

1. **参数值占位为 `?`**：形如 `[字段=>值]` 或 `[字段->值]` 的，保留字段名与分隔符，仅将值替换为 `?`。
2. **数字替换为 `#`**：日期、编号、数量、行号等所有数字均替换。
3. **压缩空白**：连续空格压缩为一个，去除首尾空格，截断至 120 字符。

**正确示例：**

| 原始报错 | 骨架 |
|---------|------|
| `[合约=>SHAG]结算价不存在` | `[合约=>?]结算价不存在` |
| `[合约=>au2606C456]结算价不存在` | `[合约=>?]结算价不存在` |
| `到期日20260219为非交易日，请修改到期日!` | `到期日#为非交易日，请修改到期日!` |
| `系统参数[参数代码=>IF_MEMBER_INQUIRY_CO]不存在` | `系统参数[参数代码=>?]不存在` |

上表前两行，不同合约、不同日期的"结算价不存在"归一化后为同一骨架，即归为同一类报错，此为骨架归一化的意义所在。

**错误示例：**

| 错误骨架 | 问题 |
|---------|------|
| `[合约=>SHAG]结算价不存在` | 未将 `SHAG` 替换为 `?`，同合约不同日期会被误判为不同类 |
| `到期日20260219为非交易日` | 未将 `20260219` 替换为 `#` |
| `到期日 # 为非交易日` | `#` 两侧不应加空格，须原位替换 |

**要点：可变部分（参数值、数字）替换为 `?` / `#`，不变部分（字段名、中文、标点）原样保留。**

### 3.4 标签规则

**一级标签 `cls`**（四选一，决定报错进入哪条处理路径）：

| 标签 | 判定条件 | 去向 |
|------|---------|------|
| `noise` | 含"成功/完成/启动/恢复/无需要发送/已处理"等噪音词，且不含业务报错词 | 噪音拦截，零 token |
| `ora` | 含 `ORA-` 或 `SQLCODE` | 标记为 Oracle 技术错误，本期不诊断 |
| `biz` | 含业务报错词（不存在/失败/异常/错误/不允许/不可/不足/不能为空/不能/冲突/超时/重复/非法/无法/请检查/未/没有/不一致/不匹配），或有非零 errcode | 进入规则匹配 / ML 路由 / LLM |
| `other` | 中文，但既非噪音亦非报错 | 兜底，回流待补规则 |

**二级标签 `biz_type`**（仅 biz 填写）：取该报错的骨架文本本身；频次未进入前 30 名的骨架统一记为 `other_biz`（交由大模型处理）。

### 3.5 数据校验清单

补充数据后，按以下六项自查：

- [ ] 每条记录的骨架已按 3.3 规则归一化（参数值为 `?`，数字为 `#`）
- [ ] 一级标签仅取 `noise`/`ora`/`biz`/`other` 之一；非 biz 的 `biz_type` 留空
- [ ] biz 的 `biz_type` 填写骨架文本或 `other_biz`
- [ ] `text` 为报错原文，未作任何改字
- [ ] `ldate` 格式为 `YYYY-MM-DD HH:MM:SS`
- [ ] 同一骨架的多条记录，其 `skeleton` 须完全一致

### 3.6 填写模板

可直接复制以下一行，按占位说明替换为实际值：

```
id,ldate,llevel,errcode,func_no,cls,biz_type,skeleton,module,deep_proc,text,lsection
〈流水号〉,〈YYYY-MM-DD HH:MM:SS〉,30,〈错误码，无填0〉,〈功能号〉,〈noise/ora/biz/other〉,〈biz填骨架或other_biz，非biz留空〉,〈归一化骨架〉,〈代码包名〉,〈过程名〉,〈报错原文不改字〉,〈调用栈〉
```

占位说明：〈〉内为需替换的内容；选填字段无值时留空（两逗号之间不填字符）。若某字段内容本身含逗号（如持仓不足骨架 `平仓错误,[会员->?]…`），须用双引号将该字段整体包裹。

填写示例（对应第五章案例）：

```
900001,2026-10-20 10:00:00,30,190101102,,biz,系统参数[参数代码=>?]不存在,系统参数[参数代码=>?]不存在,,,系统参数[参数代码=>IF_MEMBER_INQUIRY_CO]不存在,
```

## 四、各报错类别标准化示例

以下从 `rule_seed.csv` 真实数据中，按粗类各取若干示例，展示"原始报错 → 标准化骨架"的对应关系。

### 4.1 数据缺失

| 原始报错 | 骨架 |
|---------|------|
| `[合约=>SHAG]结算价不存在` | `[合约=>?]结算价不存在` |
| `系统参数[参数代码=>IF_MEMBER_INQUIRY_CO]不存在` | `系统参数[参数代码=>?]不存在` |

特征：含"不存在""无数据"，常带 `[字段=>值]` 参数。此类最适合编写诊断方案（查某表是否存在对应记录）。

### 4.2 操作失败

| 原始报错 | 骨架 |
|---------|------|
| `修改[合约=>au2607C372]失败` | `修改[合约=>?]失败` |

| `数据导入临时表失败` | `数据导入临时表失败` |

特征：含"失败"，多为写入/修改/删除未成功。是否编写诊断方案，取决于能否通过查库定位原因。

### 4.3 业务规则校验

| 原始报错 | 骨架 |

| `合约代码不能为空，请重新输入` | `合约代码不能为空，请重新输入` |

| 原始报错 | 骨架 |

|---------|------|
| `用户名或密码错误` | `用户名或密码错误` |

特征：暂未归入前述类别，需人工核对。**无法明确归类时，暂记为待分类，不应强行归入其他类别。**

## 五、新增报错类型完整录入示例

以「系统参数不存在」（biz_040）为例，演示从数据标准化到诊断规则录入的完整流程。该报错属数据缺失类、带 `[参数代码=>?]` 参数，与现有"结算价不存在"诊断方案结构一致，便于对照。

> 注：以下步骤三中的 SQL 表名仅为示例，实际表名须经业务或 DBA 确认后使用。

### 步骤一：报错标准化为训练数据

原始报错：

```
系统参数[参数代码=>IF_MEMBER_INQUIRY_CO]不存在
```

按 3.3 规则归一化：参数值 `IF_MEMBER_INQUIRY_CO` 替换为 `?`，无数字。骨架为 `系统参数[参数代码=>?]不存在`。

整理为 `dataset.csv` 一行（字段顺序与 3.6 模板一致）：

```
900001,2026-10-20 10:00:00,30,190101102,,biz,系统参数[参数代码=>?]不存在,系统参数[参数代码=>?]不存在,,,系统参数[参数代码=>IF_MEMBER_INQUIRY_CO]不存在,
```

### 步骤二：在 `rules/errors.yaml` 登记报错类型

参照现有 `settle_price_not_found` 的结构，新增一段：

```yaml
  - id: sys_param_not_found
    title: 系统参数不存在
    severity: error
    keywords: ["系统参数", "不存在"]      # 关键词命中为必要条件，每个 +10
    err_codes: [190101102]               # 错误码仅用于排序，每个 +2
    param_alias:
      "参数代码": "param_code"           # 中文参数名映射为 SQL 绑定变量名
    runbook: rb_sys_param                 # 指向 runbooks/rb_sys_param.yaml
```

字段说明：

- `id`：报错类型标识，全局唯一。
- `keywords`：**关键字段**。规则引擎要求报错原文至少命中一个关键词方匹配此类型，故须选取该报错稳定出现的关键词。
- `err_codes`：辅助排序。同一错误码可对应多种报错，故错误码不可单独决定类型。
- `param_alias`：将报错中 `[参数代码=>xxx]` 的中文参数名映射为 runbook SQL 中的英文绑定变量名。
- `runbook`：指向诊断方案文件。

### 步骤三：编写诊断方案 `rules/runbooks/rb_sys_param.yaml`

参照 `rb_settle_price.yaml` 结构：

```yaml
id: rb_sys_param
title: 系统参数不存在
steps:
  - id: param_exists
    type: sql_check
    title: 系统参数记录检查
    primary: true
    expect: {exists: true}
    sql: "SELECT PARAM_CODE, PARAM_VALUE, REMARK FROM CLEAR.TC_SYS_PARAM WHERE PARAM_CODE=:param_code"
    on_fail:
      root: "系统参数 {param_code} 未配置（参数表无此记录）"
      action:
        - "在【系统参数管理】中补录该参数代码及取值"
        - "确认该参数是否为新增业务所需，补录后重跑触发报错的业务"
default:
  root: "系统参数 {param_code} 已存在但仍报错，可能为生效状态或缓存问题"
  action:
    - "检查该参数的生效标志/启用状态"
    - "确认是否需要刷新参数缓存后重跑"
```

结构说明：

- `steps`：诊断步骤列表。`type: sql_check` 表示需查库判断；`expect: {exists: true}` 表示期望查到记录，未查到即触发 `on_fail`。
- `primary: true`：主检查。多步骤均失败时，主检查的根因优先采用。
- `sql` 中的 `:param_code` 为绑定变量，运行时以步骤二 `param_alias` 映射后的值填入。变量名须与 `param_alias` 右值一致。
- `on_fail`：查不到时的根因与处置建议，`{param_code}` 运行时替换为实际值。
- `default`：所有检查均通过（即参数实际存在）时的兜底结论。

### 步骤四：验证

录入完成后执行以下验证：

1. 运行 `python tools/verify_samples.py`，确认数据格式与标签合规。
2. 以真实报错运行 `python hybrid_diagnose.py --text "系统参数[参数代码=>IF_MEMBER_INQUIRY_CO]不存在"`，确认能匹配至 `sys_param_not_found` 并触发 `rb_sys_param` 查库。

## 六、程序输出说明

补充训练数据并录入诊断规则后，运行 `hybrid_diagnose.py` 即可获得结构化诊断报告。本章说明报告的结构、各部分含义，并给出五种处理路径的真实输出样例。

### 6.1 输出结构

诊断报告按以下顺序输出，各部分含义如下：

| 部分 | 含义 |
|------|------|
| 报错时间 / 错误码 / 报错位置 / 报错文本 | 报错基本信息。报错位置由调用栈解析，定位到代码包.过程:行号 |
| 【ML 分流】路由 / 置信度 | 一级分流结果（noise/ora/biz/other）及置信度。biz 报错另附业务类型与类型置信度，高置信走规则快速路径，低置信升级 LLM |
| 【ML 相似案例召回】 | 召回的历史相似案例，含相似度、历史频次、最近出现日期、错误码、骨架 |
| 【只读 SQL 查库证据】 | 规则引擎执行诊断树各步骤的取证结果：查到几行、返回哪些字段值。未查到记录显示"无记录（0 行）" |
| 【最终诊断】来源 | 结论由哪条路径给出，共五种：ML 快速路径（6.2）/ 规则快速路径（6.3）/ LLM 诊断大脑（6.4）/ 规则兜底（6.5）/ 兜底（6.6） |
| 问题是什么 | 根因结论，取自 runbook 的 `on_fail.root` 或 LLM 输出 |
| 附带发现 | 次要检查项的根因（如有） |
| 怎么解决 | 处置建议，取自 runbook 的 `on_fail.action` 或 LLM 输出 |
| 诊断置信度 | 本次诊断的置信度 |

### 6.2 路径一：ML 快速路径（噪音 / ORA，零 token）

噪音与 Oracle 技术错误在 ML 分流阶段即拦截，不查库、不调 LLM。输入：

```
python hybrid_diagnose.py --text "无需要发送的DAMS数据！"
```

输出：

```
================================================================================================
【TLOG 智能诊断报告 · ML 分流 + 规则取证 + LLM 大脑】
================================================================================================
报错文本 : 无需要发送的DAMS数据！
------------------------------------------------------------------------------------------------
【ML 分流】路由=noise 置信度=1.000
------------------------------------------------------------------------------------------------
【最终诊断】来源：ML 快速路径
  问题是什么：非故障提示（定时任务成功/无数据流水），无需诊断
  怎么解决：
  诊断置信度：1.000
================================================================================================
```

### 6.3 路径二：规则快速路径（高置信 + 规则命中，零 token）

ML 分流为 biz 且高置信、规则引擎命中已登记类型并查库取证，直接给出根因，不调 LLM。输入：

```
python hybrid_diagnose.py --id 3674173785
```

报错文本为 `[期权合约=>au2606C456]结算价不存在`，输出（节选关键部分）：

```
【ML 分流】路由=biz 置信度=0.997
    业务类型=[期权合约=>?]结算价不存在 类型置信度=0.982 （高置信）
【只读 SQL 查库证据（规则引擎）】
  - 交易日检查：1 行
      TRADE_DATE=20260528 | NOTE=None
  - 结算价表最新数据日期（旁证，判断数据是否已推进到报错日）：1 行
      LATEST_DATE=20260828
  - 结算价记录检查：无记录（0 行）
------------------------------------------------------------------------------------------------
【最终诊断】来源：规则快速路径（ML 高置信 + 只读查库，零 token）
  问题是什么：结算价缺失：au2606C456 在 20260528 的结算价尚未生成（闭市后处理未执行/失败，或当日行情缺失）
  怎么解决：
    1. 在【结算价管理】中手工补录该合约当日结算价
    2. 检查闭市后结算任务（PKC_MAIN / SP_CLOSE_CHECK_MAIN）是否已成功执行

  诊断置信度：0.982
```

上例中，"结算价记录检查"返回 0 行，触发 runbook `rb_settle_price.yaml` 中 `on_fail` 的根因与处置建议，`{contract}` 与 `{trade_date}` 已替换为实际值。

### 6.4 路径三：LLM 诊断大脑（低置信 / 未覆盖 / 口语化）

ML 分流低置信、规则未覆盖或输入为口语化时，升级至 LLM；LLM 综合 ML 分流、相似召回与规则取证给出结论。输入：

```
python hybrid_diagnose.py --text "结算价这个东西怎么没有同步过来呀，是不是今天行情断了？" --ldate "2026-05-28 20:07:51"
```

输出（节选关键部分）：

```

    业务类型=[合约=>?]结算价不存在 类型置信度=0.752 （低置信→升级 LLM）
【ML 相似案例召回】
  · 1.000 | 36 次 | 最近 2026-09-18 | 码 150302029/101022001/101022015
           [期权合约=>?]结算价不存在
  · ……
【只读 SQL 查库证据（规则引擎）】
  - 结算价记录检查：无记录（0 行）
------------------------------------------------------------------------------------------------
【最终诊断】来源：LLM 诊断大脑（ML 分流/召回 + 规则取证）
  问题是什么：au2606C456 在 20260528 的期权结算价记录缺失，导致收盘检查报"结算价不存在"；缺失原因需进一步核查闭市生成/导入链路。

    1. 复核期权结算价表，确认该合约当日确无结算价记录
    2. 检查 20260528 SHFE 期权闭市后处理任务……
    3. 核对当日行情/结算价源文件……

    5. 若任务日志显示已成功但仍无该合约结算价，提交开发核查
  诊断置信度：0.820
```

LLM 路径的输出多了"依据"一项（说明如何综合证据得出结论），处置建议通常更详细、分步。LLM 未配置或调用失败时，自动回退至以下两条路径之一，全程离线可跑。

### 6.5 路径四：规则兜底（LLM 不可用 + 规则命中）

```
    2. 检查闭市后结算任务（PKC_MAIN / SP_CLOSE_CHECK_MAIN）是否已成功执行
    3. 确认该合约当日是否有行情；补录或重跑成功后重新执行结算
  诊断置信度：0.982
```

### 6.6 路径五：兜底（LLM 不可用 + 规则未覆盖）

LLM 未配置或调用失败，且规则引擎未命中任何已登记类型（即该报错尚未编写 runbook），则给出兜底结论，并提示回流补规则。输入一条未登记类型的报错：

## 七、录入流程

补充一批训练数据或新增报错类型，按以下顺序执行：

1. 获取原始报错文本（工单、日志导出等）。
2. 按 3.3 规则归一化骨架（参数值为 `?`，数字为 `#`）。
3. 按 3.4 打一级标签 `cls`（noise/ora/biz/other 四选一）。
4. biz 报错打二级标签 `biz_type`（填骨架文本或 `other_biz`）。
5. 整理为 `dataset.csv` 格式（12 字段）。
6. 运行 `tools/verify_samples.py` 自查格式。
7. 高频或重要报错，按第五章补录诊断规则（`errors.yaml` 登记 + 编写 runbook），使其具备自动诊断能力；其余报错留由大模型兜底。
8. 如需更新类型路由模型，运行 `python ml/train_router.py` 重训。
