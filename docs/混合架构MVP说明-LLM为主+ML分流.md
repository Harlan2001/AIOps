# DIMPLE 数据库业务报错智能诊断 · 混合架构 MVP
## LLM 为大脑 + ML 前置分流/相似召回 + 规则只读查库 + Dimple 知识库领域知识（三证合一，已在真实 TLOG 跑通）

> 定位：面向 DIMPLE 期货/黄金清算系统（Oracle）的"已知报错查根因"。
> **以 LLM 为诊断大脑，用 ML 在入口分流、在海量历史中召回证据，用规则引擎做只读查库取证，用 Dimple 官方知识库提供机制与处置边界。**
> LLM 与 ML 均可在客户内网私有化运行；未配置 LLM 时系统自动降级为"规则 + 知识库"，全程离线可用。

---

## 一、为什么这样分工

> **LLM 负责"推理、决策、表达"——理解语义、综合证据判断根因、生成处置建议；
> ML 负责"感知、规模、记忆"——入口分流、置信度、从海量历史里找相似案例；
> 规则负责"事实、审计"——确定性的只读 SQL 查库，给 LLM 提供不会说谎的现场证据；
> 知识库负责"机制、边界、权威手册"——把官方沉淀的根因分支、成立/反证条件、必收事实、只读 SQL 模板、日志锚点、处置允许/禁止/副作用/恢复验证/回退边界提供给 LLM。**

LLM 单条强但有三个短板，正好由 ML 补齐：上下文装不下十万条日志、逐条调用贵且慢、不会从历史分布做统计。
LLM 还缺两样东西：**Dimple 业务机制的权威知识**（不能靠通用常识瞎猜业务规则）和**确定性的现场事实**（不能只读日志就断言库里状态）——前者由知识库补、后者由规则只读查库补。

## 二、处理流程

```
TLOG 报错
  │
  ├─【ML① 前置分流】TF-IDF+逻辑回归，输出 noise/ora/biz + 置信度
  │     ├ noise/ora：ML 快速路径，直接结论，不查库、不调 LLM、不检索知识库（拦掉 94% 流量）
  │     └ biz：放行
  │
  ├─【ML② 相似案例召回】字符级 TF-IDF 余弦检索，召回 Top5 历史相似案例（先验证据）
  │     （历史出现次数、最近日期、错误码、所属模块）
  │
  ├─【知识库检索】按"中文症状骨架"做本地 BM25，取 Top3 领域诊断卡（机制证据）
  │     （根因分支、成立/反证、必收事实、只读 SQL 模板、日志锚点、处置边界、来源版本）
  │
  ├─【规则引擎】对已编码类型执行只读 SQL 诊断树，产出客观证据（现场事实：查了哪张表、查到什么）
  │
  ├─【决策门】
  │     ML 高置信 且 规则命中   → 规则快速路径：直接出结论，零 token（报告仍附领域知识卡）
  │     低置信/未覆盖/口语化长尾 → 升级 LLM 诊断大脑
  │
  └─【LLM 大脑·三证合一】基于"相似案例(先验) + 领域知识(机制) + 现场查库(事实)"推理，
        以现场事实为准，输出结构化根因 + 带成立条件与回退边界的处置建议
        └ LLM 未配置/不可用 → 自动回退规则结论；规则也没有 → 诚实兜底并回流
```

**三证合一**：历史案例回答"以前发生过多少次、长什么样"；领域知识回答"按官方机制有哪些根因分支、该怎么查、怎么办、边界在哪"；现场查库回答"现在库里到底是什么状态"。三者缺一不可，且**以现场查库事实为最终准绳**。

## 三、ML 做了什么

| 模型 | 输入→输出 | 算法 | 模型大小 | 实测效果（分层测试集） |
|---|---|---|---|---|
| 一级分流器 | 报错文本→noise/ora/biz/other | 字符 TF-IDF + 逻辑回归 | 0.44 MB | 准确率 **99.98%**，macro-F1 99.96%；**业务报错召回率 100%**（不漏判） |
| 业务类型路由 | 业务报错→Top30 类型/其他 | 同上 | 1.3 MB | 准确率 **99.72%**，macro-F1 98.46% |

- 模型为 sklearn 线性模型，**纯 CPU、毫秒级、可离线、可读特征权重**，不是黑盒大模型。
- **泛化验证（ML 相比关键词规则的核心价值）**：
  - 口语化"登录时提示密码不对" → 成功召回"用户名或密码错误（历史 62 次）"，关键词规则匹配不到；
  - 口语化"结算价没同步过来，是不是行情断了" → 一级判为业务报错（正确），但类型置信度 0.75 低于阈值 → 自动升级 LLM，而不是硬分类。
- 训练方式：历史日志 + 规则标签做弱监督（无额外人工标注），后续可由 LLM 诊断结论回流形成持续学习的"数据飞轮"。

## 四、Dimple 知识库领域知识层做了什么

把 Dimple 官方维护的版本化知识库（当前版本 `kb-2026.10.14.2`、基线 `analysis-20261013.1`，含 615 条规范化知识、7 个本体切片、错误索引、诊断卡、日志模板、Mapper SQL）作为**第三类证据**接入诊断管线。

- **接入方式**：`kb/client.py` 的 `KnowledgeClient` 在进程内加载知识库自带的检索引擎（单文件、纯 Python 标准库），懒加载、异常静默降级；`config/kb.yaml` 配置开关/路径/受众/基线/top。
- **检索键用中文症状，不用数字错误码**：编排传入日志骨架 `normalize_skeleton()`，客户端再清洗为纯中文短语（去掉 `[字段=>值]` 占位符、英文、数字）。实测知识库错误码体系与 TLOG.ERRCODE 不一致——**数字码 101028602 命中 0 条，而中文症状命中准确**。
- **三证合一入提示词**：`llm/prompts.py` 的 SYSTEM 明确"历史案例=先验、领域知识=机制手册、现场查库=事实，以现场为准；知识未现场核实、只读 SQL 未执行不得声称已执行；遵守处置允许/禁止/副作用/回退边界"。
- **报告呈现**：报告新增【领域知识卡】段落（根因分支、成立/反证、必收事实、相关参数、只读 SQL 模板、日志锚点、处置边界、来源版本与文件行号）。
- **安全边界**：
  - 知识库只读 SQL **默认不自动执行**（`execute_kb_sql=false`），仅作建议喂给 LLM/展示；经人工审核、核对现场方言/表结构/权限后才派生为规则 runbook；**唯一可执行查库层始终是规则引擎**。
  - 知识卡固定标注"**冻结源码取证、未现场核实、只读 SQL 未执行**"。
  - 客户/基线门禁：`internal` 全集仅内部分析、不得外发；交付客户必须用 `dimple_install` 生成客户专包。
- **零额外基础设施**：纯本地 BM25、离线、无网络、无数据库、无 API key、无向量库。
- **可降级**：知识库缺失/关闭/异常时自动跳过，主流程不受影响。

**知识检索自测命中（`tools/test_kb.py`）**：

## 五、成本测算
| 处理路径 | 当前（仅 3 类规则） | 规则补齐 Top30（覆盖业务 93.5%） |
|---|---|---|
| ML 快速路径（噪音/ORA，零 token） | 94.03% | 94.03% |
| 规则快速路径（高置信+查库，零 token） | 0.30% | 5.55% |
| **真正调用 LLM** | 5.64% | **0.40%** |

> **结论：ML 在入口已拦掉 94% 流量；规则补齐后，平均每 250 条错误只有 1 条需要真正调用 LLM。**
> 知识库检索是本地 BM25、零 token、毫秒级，**不增加任何 LLM 成本**；即使按 5.95% 业务报错全量计算，LLM 调用也被压缩到极小比例，私有化部署后成本几乎可忽略。

## 六、端到端实测场景

1. **结算价不存在（ID 4964465949）**：ML 分流 biz（置信 0.997）、类型"期权结算价不存在"（0.989 高置信），召回 Top1 完全匹配（36 次），规则查库得"结算价记录 0 行 + 最新数据日期 20260828 + 交易日历缺失"，知识库命中 `settle-mgmt-close-postprocess`（306 篇），**走规则快速路径零 token** 输出主根因+附带发现+领域知识卡。
2. **持仓不足（ID 4811525544，已用真实 qwen3.8-max 验证三证合一）**：ML 分流 biz（0.994）、类型（0.96），召回同模式 32 次；规则查库得客户 Au(T+N1) 买 1999/卖 2202、持仓明细 `BS_FLAG=1` 且 **TRADER_NO=None**；知识库命中 `business-position-decision`，其"真实缺仓 / 交易员归属错误 / 合法调转"三分支恰好对应现场疑点。LLM 综合三证后：
   - 准确指出"在指定交易员 trader 维度下可平不足 1 手，但明细 `TRADER_NO=None`，尚不能区分真实缺仓 / 交易员归属错误 / 重复超额平仓"，证据不足不下定论；
   - 明确写出"**知识库只读 SQL 未在现场执行，不能据此认定现场状态**"，以现场查库为准；
   - 处置从泛泛几步扩展为 **8 步带边界流程**：暂停任务→按成交号查成交→分层（客户层/交易员层/空交易员层）核算可平量→查 IF_TRADER_CTL 等参数→按权威证据分流（补录冲正 / 标准归属调整 / 持仓调转）→**禁止虚增持仓改库**→恢复后做数量守恒与下游核对、已切日按补偿冲正处理。
   - LLM 不可用时规则结论兜底。
3. **高频但未建规则（存续期变更失败，3380 次，已用真实 LLM 验证）**：ML 准确识别（0.993）并召回历史（多发生于 PKC_INQUIRE_MANAGE），规则未覆盖→升级 LLM；LLM 基于"仅有报错文本、无错误码/参数/查库证据"的情况**诚实给出低置信度 0.35**，引导先收集上下文、定位模块表名、只读核对主表、检查上游流程，绝不臆测具体根因。LLM 未配置时则兜底为"未命中规则、请人工/补规则"。
4. **噪音（ID 4977577595）**：ML 快速路径直接判定"非故障提示"，毫秒级零成本，不查库、不检索知识库、不调 LLM。

## 七、合规与部署

- **LLM（已接入真实端点）**：`config/llm.yaml` 现已接入阿里云 MaaS OpenAI 兼容网关（compatible-mode），模型 `qwen3.8-max`（该 Key 实测授权，备选 `deepseek-v4-pro`）。面向客户交付时改为内网私有化部署（vLLM / Ollama / 内网网关，路径同为 `.../v1`），数据不出内网、无公网 token。`enabled=false` 或调用失败/超时，系统自动降级为"规则 + 知识库"、离线可跑。
  - **选模型**：`python tools/llm_models.py` 列出网关全部模型，`python tools/llm_probe_models.py` 逐个探测本 Key 实际有权限的模型（`/models` 能列出 ≠ 有调用权限，未授权会返回 403 `access_denied`）。
  - **自检**：`python tools/llm_ping.py` 做最小连通测试；`python tools/test_llm_bridge.py` 用本地 mock 离线验证调用链路。
  - **安全**：`config/llm.yaml` 含密钥、已加入 `.gitignore`，切勿提交/外发；对外只提供 `config/llm.yaml.example` 模板。
- **ML 模型**：两个 sklearn 线性模型（共约 1.7MB），CPU 即可，无需 GPU；随规则/数据迭代离线重训。
- **Dimple 知识库**：纯本地只读文件快照（BM25，纯标准库，无网络/数据库/API key/向量库）；`config/kb.yaml` 配置 `kb_root/audience/baseline/top/execute_kb_sql`。交付客户用 `dimple_install` 生成**客户专包**挂载到 `/app/kb`，内部全集不得外发；知识快照不含源码、凭据、客户数据；版本更新走知识库自带流程、产品侧只替换快照并回归。
- **查库**：全程只读，代码层拦截一切写 SQL；知识库的只读 SQL 默认不执行，必须经人工审核后派生为 runbook 才由规则引擎执行。
- **可解释**：报告标注每一步由 ML / 知识库 / 规则 / LLM 完成，LLM 结论附历史案例、领域知识卡与查库证据，可审计、可复核。

## 十、对应"ML 一定要有 / 不只靠 LLM"的落地结论

- ML 不是摆设，占据了**两个不可替代的关键环节**：入口分流（省成本、提速度、泛化变体）与相似案例召回（解决 LLM 上下文有限、无法在海量日志里做统计关联的问题）。
- 知识库补上了**业务机制与处置边界**：让 LLM 不再凭通用常识猜 Dimple 规则，处置建议带成立条件、副作用、恢复验证和回退边界，并能按权威分支快速产出 runbook 候选。
- 决策门实现了**置信度分级**：高置信高频问题 ML+规则秒级处理（零 token），疑难/长尾才升级 LLM——LLM 始终是"大脑"，但算力只花在刀刃上；知识库与规则路径全程零 token。
- 规则补齐（含从知识库诊断卡批量派生）+ LLM 诊断结论回流，可进一步训练 ML 根因模型（数据飞轮），让系统越用越省、越用越准。
